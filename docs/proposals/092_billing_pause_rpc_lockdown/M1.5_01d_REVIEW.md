# M1.5｜01d 專項審查與最小修復順序

> 依據：repo 的 migrations 001–091 與 `web/src`。正式站的實際狀態以 `00d_inspect_identity_readonly.sql` 的輸出為準。
> 本文件**沒有**對任何 Supabase 執行過 SQL。

## 1. 允許一般使用者取得平台管理員的位置

平台管理員的唯一判斷來源是 `app_user_profiles.primary_role = 'platform_admin'`：
- DB 端：`is_platform_admin()`（002 建立，007 改為 SECURITY DEFINER）。
- App 端：`middleware.ts`、`(admin)/layout.tsx`、所有 `/api/admin/*` 都只查 `primary_role`。

| 物件 | 來源 | 問題 |
|---|---|---|
| Policy `app_user_profiles_update_self_or_admin` | 002 | `using / with check (id = auth.uid() or is_platform_admin())`，沒有限制欄位，本人可改任何欄位，**包括 primary_role** |
| Policy `app_user_profiles_insert_self` | 002 | 尚未建立 profile 的帳號，可以直接 insert 成 `platform_admin` / `host` |
| Policy `Platform admin update users` | 007 | 管理員可以改任何人（正常需求）；一旦有人自我提升，這條讓他也能改別人 |
| GRANT | Supabase 預設 | authenticated 對 `app_user_profiles` 有完整 INSERT / UPDATE 權限，RLS 是唯一防線 |
| Function `is_platform_admin()` | 007 | **不檢查 `is_active`**：被停權的管理員仍是管理員 |
| Trigger | — | 修補前除了 `updated_at` 外沒有任何 trigger |
| `user_role_memberships` | 072 | 本人只能 insert / update `role = 'player'`，**不是**提權路徑。App 也不用它判斷管理員 |
| `auth.users` metadata | — | App 不信任 `user_metadata` / `app_metadata` 的角色，也沒有 `auth.users` trigger，**不是**路徑 |
| SECURITY DEFINER 函式 | repo | repo 內沒有會依使用者輸入寫入 `primary_role` 的 DEFINER 函式。正式站可能有手動建立的，由 00d 的 G 段確認 |

取得管理員之後能做什麼：
- 讀取 `platform_line_integration`：LINE Messaging access token、LINE Login secret。
- 讀取 `kb_payment_provider_configs`。
- 讀寫所有會員資料。
- 使用 `/api/admin/*`：刪除使用者、改角色、分潤調整等。

## 2. 停權與帳號恢復相關欄位

| 欄位 | 寫入者 | 修補前的問題 |
|---|---|---|
| `is_active` | 管理頁（管理員 JWT）、`bulk-disable` / `bulk-restore`（service_role）、帳號刪除（service_role） | 被停權者可以自己改回 `true` |
| `is_deleted`、`deleted_at`、`account_deleted_at`、`anonymized_at`、`deleted_display_name_snapshot`（081） | 只有帳號刪除 API（service_role） | 已刪除者可以自己改回 `is_deleted = false`；但 Auth 已被 ban，實際無法再登入 |
| `line_oa_user_id`（profile；正式站不一定有這個欄位） | 只有 LINE webhook（service_role） | 可以自己填別人的 LINE UID |

**另一個發現（01d 沒有處理，建議下一階段處理）：`is_active=false` 在系統中沒有任何強制力。**
- middleware、登入流程、RLS、`is_platform_admin()` 都不看 `is_active`。被停權者仍可登入並照常操作。
- 建議：
  - `is_platform_admin()` / `is_host()` 加上 `is_active`。
  - middleware 擋下停權帳號。
  - 停權時同步 ban Auth。
- 這會改變現有行為，需要另外核准，因此不放進 01d。

## 3. 01d 是否限制 anon / authenticated / PUBLIC

- 修補方式是 BEFORE INSERT / UPDATE trigger。**預設拒絕**：只有本身就能略過 RLS 的角色不受限，也就是 `rolsuper` 或 `rolbypassrls` 為真的角色（service_role、postgres），以及以它們為 owner 的 SECURITY DEFINER 函式。
- 因此 anon、authenticated，以及任何繼承 PUBLIC 權限的自訂角色都受限。測試有一個只帶 PUBLIC 式權限的自訂角色 `rogue`，被擋下。
- 受保護欄位：`primary_role`、`is_active`、`is_deleted`、`deleted_at`、`account_deleted_at`、`anonymized_at`、`deleted_display_name_snapshot`、`line_oa_user_id`。
- 以 `to_jsonb` 比對欄位，正式站缺少 081 的欄位時也不會報錯。測試涵蓋「沒有 081 欄位」與「有 081 欄位」兩種 schema。
- 輔助函式 `kb092_caller_is_active_platform_admin()`：anon 沒有 EXECUTE 權限，authenticated 和 service_role 有。

## 4. 真正平台管理員的合法操作

| 操作 | 修補後 |
|---|---|
| `/admin/users` 頁面改角色、停權 / 復權（管理員 JWT 直接 PATCH） | ✅ 呼叫者須為**啟用中**的平台管理員 |
| `bulk-update-role` / `bulk-disable` / `bulk-restore` / 刪除使用者 API（service_role） | ✅ 不受影響 |
| SQL Editor（postgres）手動改角色，例如 `fix_admin.js` 的做法 | ✅ 不受影響 |
| 管理員降級自己 | ✅ 允許，不會把自己鎖住 |
| **被停權的**管理員改別人的角色 | ❌ 新增限制。正式站可能有停權中的管理員，請看 00d 的 J 段 |

| 流程 | 寫法 | 影響 |

| LINE webhook：綁定 / 解除 `line_oa_user_id` | service_role | 無 |

## 7. 需要調查的異常紀錄（00d 會列出）

| 段落 | 內容 | 級別 |
|---|---|---|
| J | 每個平台管理員，含遮罩名稱 / Email、登入方式、最後登入、是否有稽核紀錄、90 天內的管理動作數 | 預期之外的管理員 = REVIEW |
| L1 | 最後一筆稽核是停權、但現在是啟用（可能自行解除停權） | RISK |
| L2 / L3 | 已匿名化卻 `is_deleted = false`；已刪除卻仍啟用 | RISK |
| L4 / L5 | 管理類角色沒有對應 membership；建立後被修改過，但沒有任何角色稽核紀錄 | REVIEW |
| L7 | 測試網域帳號（example.com 等）存在於正式站 | 管理類角色為 RISK |
| L6 | LINE 與金流機密：只顯示有無值與最後更新時間 | 有異常管理員時，這些必須輪替 |

注意：`/admin/users` 頁面由瀏覽器直接寫 `kb_audit_logs`，但該表沒有 INSERT policy，寫入會靜默失敗。所以「管理頁改過角色」本來就沒有稽核紀錄，L4 / L5 會有誤報，需要人工比對。

若發現不明管理員，**處置需另外核准**：
1. 以 SQL Editor 或 `bulk-update-role` 降級。
2. ban 該 Auth 帳號。
3. 輪替 LINE Messaging token、LINE Login secret、ECPay key。
4. 視情況輪替 Supabase service_role key。
5. 檢視該帳號的 `kb_audit_logs` 與分潤異動。
